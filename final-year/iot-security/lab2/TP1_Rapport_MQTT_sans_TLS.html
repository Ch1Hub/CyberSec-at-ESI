1Objectifs et périmètre

Ce premier TP établit la situation de départ de la série : un objet connecté parle MQTT en clair sur le port 1883. L'objectif est de montrer, capture à l'appui, que l'authentification par nom d'utilisateur et mot de passe ne protège en rien la confidentialité ni l'intégrité des échanges.

Objectif 1
Programmer un client MQTT authentifié

Équivalent de l'ESP8266 + PubSubClient : connexion avec esp01 / esp01pass, publication d'une température toutes les 5 s.

Objectif 2
Capturer et isoler le CONNECT

Filtrer le trafic MQTT, ouvrir le paquet Connect Command et lire les champs User Name et Password.

Objectif 3
Lire les sujets et les charges utiles

Suivre le flux TCP et reconstituer la conversation applicative : sujet capteurs/esp01/temp et valeurs de température.

Objectif 4
Mesurer l'impact pour un attaquant

Réutiliser les identifiants capturés pour publier une fausse mesure et observer sa diffusion.

Périmètre éthique
Toutes les manipulations ont été réalisées sur des objets simulés et un broker local, sur l'interface lo uniquement. Aucun scan, aucune connexion vers un équipement tiers. Les secrets du laboratoire restent confinés à ce rapport et aux fichiers du TP.

3Mise en place du broker et de l'objet

Le broker est lancé avec un fichier de configuration minimal : écoute sur le port 1883, authentification par fichier de mots de passe, aucun chiffrement. Le fichier passwd est créé avec mosquitto_passwd et contient l'utilisateur esp01.

Le script reprend le sketch du sujet : connexion au réseau Wi-Fi (simulée), CONNECT MQTT avec les identifiants, puis publication périodique de la température. 4.2 Lire les identifiants dans le paquet CONNECT

Le paquet Connect Command de l'objet est la trame 14. Le dissecteur MQTT expose directement les champs utiles :

Le drapeau 0xc2 confirme que les bits User Name Flag et Password Flag sont positionnés. Le mot de passe n'est pas haché : MQTT 3.1.1 le transporte tel quel dans la charge utile du CONNECT. Le broker le vérifie à l'arrivée, mais rien ne protège son transit. La trame 4 est le CONNECT de l'abonné de contrôle : son Client ID est vide (généré par le broker), mais les mêmes identifiants esp01 / esp01pass y sont également visibles.

  • La cartographie des sujets — capteurs/esp01/temp, qui indique à la fois le type de donnée et l'identité de l'objet.
  • Les données métier — les quatre valeurs de température (20.0 à 22.1), qui suffisent à profiler l'activité du capteur.

4.4 Exploiter la capture

Avec les identifiants dérobés, un attaquant du même réseau se connecte au broker et publie une valeur arbitraire sur le sujet de l'objet. Aucune ACL n'est configurée : le broker accepte la publication et la diffuse à tous les abonnés.

Preuve dans la capture d'injection
$ tshark -r captures/tp1_injection.pcapng \
    -Y 'mqtt.msgtype == 3 && mqtt.topic == "capteurs/esp01/temp"' \
    -T fields -e frame.number -e mqtt.topic -e mqtt.msg
18    capteurs/esp01/temp    3939      # 3939 = « 99 » en hexadécimal
20    capteurs/esp01/temp    3939

La trame 18 est la publication de l'attaquant, la trame 20 sa retransmission par le broker vers l'abonné. La valeur 99 °C est acceptée sans contrôle : l'intégrité des mesures n'est pas garantie.

Point clé
allow_anonymous false empêche seulement les connexions sans identifiants. Dès qu'un mot de passe circule en clair, l'authentification devient une formalité contournable : il suffit de l'observer une fois. La confidentialité et l'intégrité exigent un chiffrement du transport (TLS), pas seulement une vérification d'identité.

6Réponses aux questions

Q1 Dans quel paquet et à quel endroit se trouvent le nom d'utilisateur et le mot de passe ? Pourquoi sont-ils lisibles alors que le broker exige une authentification ?

Ils se trouvent dans le paquet CONNECT (paquet n° 14 de la capture), dans la charge utile MQTT, aux champs User Name et Password. Le dissecteur les affiche directement et la vue hexadécimale les confirme. MQTT 3.1.1 ne prévoit aucun chiffrement de ces champs : le mot de passe est transmis en clair, sans hachage ni challenge.

Le broker exige une authentification, mais celle-ci est vérifiée à l'arrivée. Entre l'objet et le broker, le trafic circule sur TCP en clair (port 1883) : toute personne qui capture le réseau lit les identifiants. Authentifier n'implique pas protéger le secret pendant le transport ; c'est précisément la confusion que ce TP met en évidence.

Q2 Que montre « Suivre le flux TCP » ? Citez trois informations qu'un attaquant en tire.

Le suivi de flux reconstitue la conversation applicative complète, y compris les paquets de contrôle MQTT. On y voit le CONNECT (esp01 / esp01pass), le CONNACK, puis les PUBLISH successifs vers capteurs/esp01/temp avec leurs valeurs. Trois informations directement exploitables :

  • Les identifiants : réutilisables pour se connecter au broker et se faire passer pour l'objet ;
  • Les sujets : ils révèlent la structure de l'installation et les topics de commande éventuels ;
  • Les données : les mesures et leur périodicité, qui permettent de profiler le capteur et de préparer une injection crédible.
Q3 L'option allow_anonymous false suffit-elle à protéger la communication ? Justifiez à partir de la capture.

Non. Cette option interdit les connexions sans identifiants, mais elle ne chiffre rien. La capture montre que le mot de passe circule en clair dans le CONNECT : un attaquant qui l'a observé une seule fois peut se connecter légitimement, sans jamais avoir besoin de l'option anonyme. L'injection de la fausse mesure (99 °C) le démontre : le broker ne distingue pas l'objet de l'attaquant qui rejoue ses identifiants.

Autrement dit, allow_anonymous false ferme la porte aux curieux qui n'ont pas d'identifiants ; elle ne protège ni la confidentialité du mot de passe, ni l'intégrité des messages, ni l'identité réelle du client.

Q4 Quelle est la différence entre authentifier un client et chiffrer la communication ? Lequel manque ici ?

Authentifier, c'est vérifier l'identité déclarée : le broker compare le couple utilisateur/mot de passe à son fichier. Chiffrer, c'est rendre le contenu illisible pour un observateur et en garantir l'intégrité en transit (TLS).

Ici, l'authentification est présente mais faible (secret partagé, rejouable), et le chiffrement manque totalement : le port 1883 transporte le CONNECT, les sujets et les charges utiles en clair. Les deux propriétés sont indépendantes : on peut authentifier sans chiffrer (c'est le cas), ou chiffrer sans authentifier mutuellement (TLS serveur seul, TP2).

Q5 Proposez une mesure qui rendrait la capture inexploitable sans changer le code applicatif de l'ESP8266.

Activer TLS sur le broker (port 8883, certificat serveur signé par une CA de laboratoire) et faire pointer le client vers ce port avec une ancre de confiance. Côté ESP8266, on remplace WiFiClient par WiFiClientSecure et on charge ca.crt ; les appels connect() et publish() ne changent pas. C'est exactement l'objet du TP2.

En complément (défense en profondeur) : identifiants uniques par objet, ACL par topic, limitation de débit et segmentation réseau. Mais sans TLS, ces mesures ne empêchent pas l'écoute du mot de passe.

8Durcissement et transition vers le TP2

Le TP1 s'arrête volontairement à l'état non sécurisé. Le durcissement attendu au TP2 est un changement de transport, pas de logique applicative :

Cible TP2 — extrait de configuration Mosquitto
listener 8883
allow_anonymous false
password_file /etc/mosquitto/passwd
cafile   /etc/mosquitto/certs/ca.crt
certfile /etc/mosquitto/certs/broker.crt
keyfile  /etc/mosquitto/certs/broker.key
tls_version tlsv1.2
Cible TP2 — côté objet (Arduino)
BearSSL::WiFiClientSecure wifi;
BearSSL::X509List caCert(CA_CERT);
wifi.setTrustAnchors(&caCert);
mqtt.setServer("192.168.1.10", 8883);
Ce qu'il faut retenir
Le mot de passe reste un secret partagé : TLS le protège en transit, mais ne prouve pas l'identité de l'objet si le secret est volé. Le TP2 apporte la confidentialité et l'authentification du serveur ; le TP3 ajoutera le certificat client (mTLS) pour une identité non rejouable.

9Annexe A — script complet

esp8266_sim.py
#!/usr/bin/env python3
"""Simulateur d'ESP8266 — TP1 : client MQTT en clair (port 1883).

Reproduit le sketch Arduino du TP1 sans matériel radio :
  - Wi-Fi « IOT-LAB »
  - broker 127.0.0.1:1883
  - utilisateur esp01 / mot de passe esp01pass
  - publication de capteurs/esp01/temp toutes les 5 s
"""
import os
import threading
import time

import paho.mqtt.client as mqtt

SSID = os.getenv("WIFI_SSID", "IOT-LAB")
BROKER = os.getenv("MQTT_HOST", "127.0.0.1")
PORT = int(os.getenv("MQTT_PORT", "1883"))
MQTT_USER = os.getenv("MQTT_USER", "esp01")
MQTT_PASS = os.getenv("MQTT_PASS", "esp01pass")
CLIENT_ID = os.getenv("MQTT_CLIENT_ID", "esp01")
TOPIC = os.getenv("MQTT_TOPIC", "capteurs/esp01/temp")

connected = threading.Event()


def on_connect(client, userdata, flags, reason_code, properties):
    connected.set()
    print(f"CONNACK : {reason_code}", flush=True)


def on_disconnect(client, userdata, flags, reason_code, properties):
    print(f"connexion perdue ({reason_code}) — reconnexion", flush=True)


def main() -> None:
    print(f"Wi-Fi : connecté au réseau {SSID} (simulation)", flush=True)
    client = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id=CLIENT_ID)
    client.username_pw_set(MQTT_USER, MQTT_PASS)
    client.on_connect = on_connect
    client.on_disconnect = on_disconnect
    client.connect(BROKER, PORT, keepalive=30)
    client.loop_start()
    connected.wait(timeout=5)
    t0 = time.time()
    n = 0
    while True:
        # Télémesure simulée : 20.0 .. 25.0, valeur différente à chaque envoi
        temp = 20.0 + ((n * 0.7) % 5.0)
        payload = f"{temp:.1f}"
        client.publish(TOPIC, payload)
        print(f"PUBLISH {TOPIC} = {payload}", flush=True)
        n += 1
        time.sleep(5)


if __name__ == "__main__":
    main()
